# Pixel Barber — Backend Schema, Auth & API Design

**Document status:** Input document for Claude Code (or any engineer) to scaffold the database and backend
**Version:** 1.0
**Date:** 9 September 2026
**Companion to:** `pixel-barber-prd.md` (business rules, data model summary, RBAC table), `pixel-barber-app-flow.md` (screens that read/write this schema), `pixel-barber-tech-stack.md` (Supabase/Next.js/Edge Function versions this schema targets) — this document does not repeat any of their content, only adds the concrete database, auth, RLS, and API layer needed to start writing migrations.

**Decisions locked for this document**, from the clarifying round before it was written: queue capacity gets a nullable per-branch cap, off by default; cross-branch transfer is held for Phase 2 with no schema footprint yet; VIP/loyalty is skipped entirely for v1; no-show history stays informational but carries a forward-compatible enforcement flag; data retention is 3 years from last activity, enforced by anonymizing (not hard-deleting) historical records; customers and staff share one `auth.users` table via Supabase Auth, split into two profile tables; a barber's shared-station PIN mints a real Supabase session rather than an app-level-only check; business content (branch/service names and descriptions) is stored once, not per-locale — only UI chrome is translated; scheduled transitions (appointment activation, grace-period expiry) run on `pg_cron` inside Postgres; and the "key API endpoints" section below covers only the custom endpoints that need real server logic, since standard CRUD is auto-generated by PostgREST under RLS.

## 0. How This Schema Is Organized

Everything here is one Supabase Postgres database. There is no per-branch schema separation and no multi-tenant isolation layer — per PRD section 7, Pixel Barber is one business, so every table rolls up cleanly without a tenant_id anywhere. Section 1 covers the overall shape (schemas, extensions, conventions). Sections 2–3 cover identity: how `auth.users` relates to customers and staff, and how role/branch scoping reaches Postgres for RLS to use. Sections 4–13 are the tables themselves, grouped the same way the PRD's own section 36 groups them, each with its DDL and the business rules from the PRD it encodes. Section 14 is Row-Level Security, written once as a set of principles plus the actual policy SQL for every table where the pattern isn't purely mechanical. Section 15 covers the scheduled/triggered logic (ticket numbering, grace-period expiry, appointment activation, wait-time-supporting stats). Section 16 covers Realtime. Section 17 covers the custom API surface. Section 18 covers retention and erasure. Section 19 is naming/migration conventions. Section 20 lists what later phases will add on top of this without breaking it.

## 1. Conventions, Extensions, Schemas

Tables live in the `public` schema except where noted. Table names are `snake_case` and plural (`branches`, `queue_tickets`); columns are `snake_case`; primary keys are `id uuid default gen_random_uuid()` everywhere except the two tables whose primary key *is* `auth.users.id` (section 2). Every table has `created_at timestamptz not null default now()`; tables whose rows can be edited after creation also have `updated_at timestamptz not null default now()`, kept current by one shared trigger (`set_updated_at()`) attached per table rather than repeated application logic. Money is `numeric(10,2)` in GHS, never `float`. All timestamps are `timestamptz`, stored in UTC; the application renders them as GMT (PRD section 11) — since Ghana has no DST, this is a display concern only, never a schema one. Enumerated states use Postgres `enum` types (not free-text with a check constraint) so an invalid state is a write-time error, not a data-quality problem discovered later.

Extensions required: `pgcrypto` (for `gen_random_uuid()`), `pg_cron` (section 15), `pg_net` (only if a cron job needs to call an Edge Function over HTTP rather than doing everything in SQL — used sparingly, see section 15.3).

```sql
create extension if not exists pgcrypto;
create extension if not exists pg_cron;
create extension if not exists pg_net;

create or replace function set_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at = now();
  return new;
end;
$$;
```

## 2. Identity: `auth.users` and the Two Profile Tables

Supabase Auth's `auth.users` is the single source of truth for *credentials* (password hashes, OTP state, sessions, refresh tokens) — nothing here re-implements that. What this schema adds are two profile tables that each 1:1-extend a row in `auth.users`, per the locked decision in this document's header:

**`customers`** — a customer's `auth_user_id` is **nullable**. A customer created through self-service or the Onboarding Wizard (App Flow section 5) always has one, set at signup. A customer created by staff walk-in registration (PRD section 13) with no phone number, or with a phone number but who never completes the Onboarding Wizard, has **no** `auth.users` row at all yet — they exist purely as a CRM/queue record. When that same phone number later completes onboarding (App Flow section 6's "create an account" banner, or a fresh signup), the new `auth.users` row is linked by setting `auth_user_id` on the *existing* `customers` row (matched by `phone_e164`) rather than creating a second customer — this is what makes the App Flow's "ticket links to the new account automatically by phone match" behavior (section 3, section 10) a straightforward `UPDATE`, not a merge of two histories.

**`staff_users`** — a staff member's `auth_user_id` is **not** nullable; every staff account (Owner, Branch Manager, Receptionist, Barber, Analyst) requires real credentials before it can do anything, per PRD section 32's "no shared logins." A `staff_users` row with role Barber additionally gets a row in `barbers` (section 6) holding barber-specific operational fields — the login/identity lives in `staff_users`, the "resource being scheduled and assigned" lives in `barbers`, linked 1:1.

```sql
create table customers (
  id                          uuid primary key default gen_random_uuid(),
  auth_user_id                uuid unique references auth.users(id) on delete set null,
  name                        text not null,
  phone_e164                  text unique,                     -- nullable: a walk-in with genuinely no phone
  email                       text,
  avatar_key                  text,                            -- key into the predefined avatar library (App Flow 5, step 4) — not a Storage object
  preferred_branch_id         uuid references branches(id),
  push_lead_minutes_primary   smallint not null default 10,     -- PRD section 20's editable 10-/5-minute defaults
  push_lead_minutes_secondary smallint not null default 5,
  push_enabled                boolean not null default true,
  sms_backup_enabled          boolean not null default true,
  no_show_count               integer not null default 0,       -- PRD 21/28: informational reliability signal
  late_cancellation_count     integer not null default 0,
  requires_confirmation_call  boolean not null default false,   -- forward-compat flag from the no-show policy decision; unused by any v1 logic
  is_anonymized               boolean not null default false,   -- section 18
  anonymized_at               timestamptz,
  last_activity_at            timestamptz not null default now(),
  created_at                  timestamptz not null default now(),
  updated_at                  timestamptz not null default now()
);
create trigger trg_customers_updated_at before update on customers
  for each row execute function set_updated_at();
create index idx_customers_last_activity on customers(last_activity_at) where is_anonymized = false;
```

```sql
create type staff_role as enum ('owner','branch_manager','receptionist','barber','analyst');

create table staff_users (
  id            uuid primary key default gen_random_uuid(),
  auth_user_id  uuid not null unique references auth.users(id) on delete restrict,
  name          text not null,
  phone_e164    text unique,
  email         text unique,
  role          staff_role not null,
  pin_hash      text,              -- set only for barbers who use shared-station PIN login (section 3.3)
  is_active     boolean not null default true,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
create trigger trg_staff_users_updated_at before update on staff_users
  for each row execute function set_updated_at();
```

Role is a single enum column rather than a foreign key to a `roles` table, because PRD section 32's six roles are a fixed, small, product-defined set — what *is* dynamic, per that same section's "composable capabilities... so a role can be added later without a data-model change," is which capabilities each role carries, which is exactly what the `capabilities` / `role_capabilities` tables in section 3.2 are for. Adding a seventh role (the PRD's own example: Regional Manager) means adding one enum value and its capability rows — no table restructure.

## 3. Authorization: Capabilities, RLS Claims, and PIN Login

### 3.1 Why capabilities are a table, not hard-coded

PRD section 32 is explicit that permissions must be "composable capabilities... assigned to roles, rather than hard-coded per-role checks." This schema models that literally:

```sql
create table capabilities (
  key         text primary key,   -- e.g. 'manage_branches', 'edit_pricing', 'view_reports'
  description text not null
);

create table role_capabilities (
  role       staff_role not null,
  capability text not null references capabilities(key),
  primary key (role, capability)
);
```

Seed rows for `capabilities` map directly onto the "Can do" column of the PRD's RBAC table (section 32): `manage_branches`, `manage_staff`, `edit_pricing`, `edit_hours`, `view_business_reports`, `view_branch_reports`, `manage_barber_schedules`, `handle_escalations`, `register_walkins`, `edit_tickets`, `cancel_tickets`, `check_in_customers`, `message_customers`, `broadcast_messages`, `manage_own_queue` (a barber acknowledging/flagging/completing their own current ticket only), `view_audit_log`. `role_capabilities` then assigns each to Owner/Branch Manager/Receptionist/Barber/Analyst exactly per that table — Analyst gets every `view_*` capability and nothing else; Barber gets only `manage_own_queue`.

### 3.2 Getting role, staff identity, and branch scope into RLS

RLS policies run inside Postgres and only have access to what's in the request's JWT (via `auth.jwt()`) or what a `SECURITY DEFINER` helper function looks up from `auth.uid()`. Rather than stuffing capability lists into the JWT (which would go stale the moment `role_capabilities` changes, until the user's token is refreshed), this schema takes the simpler, always-current path: the JWT carries only `app_role` and, for staff, the list of branch IDs they're assigned to; every other check is a live lookup.

```sql
-- Runs as a Supabase Auth "Custom Access Token" hook (configured in the Supabase
-- dashboard under Authentication → Hooks), so every newly issued token already
-- carries these claims — no extra round-trip per request.
create or replace function custom_access_token_hook(event jsonb)
returns jsonb
language plpgsql
security definer
as $$
declare
  claims jsonb := event->'claims';
  v_staff record;
  v_branch_ids uuid[];
begin
  select id, role into v_staff from staff_users where auth_user_id = (event->>'user_id')::uuid;
  if found then
    select coalesce(array_agg(branch_id), '{}') into v_branch_ids
      from staff_branch_assignments where staff_user_id = v_staff.id;
    claims := jsonb_set(claims, '{app_role}', to_jsonb(v_staff.role::text));
    claims := jsonb_set(claims, '{staff_id}', to_jsonb(v_staff.id::text));
    claims := jsonb_set(claims, '{branch_ids}', to_jsonb(v_branch_ids));
  else
    claims := jsonb_set(claims, '{app_role}', to_jsonb('customer'::text));
  end if;
  return jsonb_set(event, '{claims}', claims);
end;
$$;
```

Three small helpers every RLS policy below builds on:

```sql
create or replace function auth_role() returns text
language sql stable as $$ select coalesce(auth.jwt()->>'app_role', 'anon') $$;

create or replace function auth_staff_id() returns uuid
language sql stable as $$ select nullif(auth.jwt()->>'staff_id','')::uuid $$;

create or replace function auth_branch_ids() returns uuid[]
language sql stable as $$
  select coalesce(array(select jsonb_array_elements_text(auth.jwt()->'branch_ids'))::uuid[], '{}')
$$;

create or replace function has_capability(cap text) returns boolean
language sql stable as $$
  select exists (
    select 1 from role_capabilities
    where capability = cap and role = auth_role()::staff_role
  )
$$;

create or replace function in_branch_scope(target_branch uuid) returns boolean
language sql stable as $$
  select auth_role() = 'owner' or target_branch = any(auth_branch_ids())
$$;
```

`auth_role() = 'owner'` bypassing branch scope is the one hard-coded shortcut in this whole model, matching the PRD's own description of Owner as seeing "all branches, all data" unconditionally rather than via an assignable capability.

### 3.3 Barber shared-station PIN login

Per the locked decision, a PIN does not just switch which barber's view is shown — it mints a real Supabase session so every RLS policy below applies exactly as it would to a personal-device login. This is a custom Edge Function (`pin-login`, service-role key, never exposed to any client bundle) rather than anything in `apps/staff`'s own Next.js server:

1. The station app POSTs `{ branch_id, pin }` to the `pin-login` Edge Function.
2. The function looks up `staff_users` where `role = 'barber'`, `pin_hash` matches (via `crypt()`/bcrypt comparison, never plain-text), and the barber is assigned to that `branch_id` (via `staff_branch_assignments`, or as their `barbers.today_branch_id`, section 6). A PIN is only ever checked against barbers who can legitimately be at *that* station's branch — a valid PIN for the wrong branch fails.
3. On match, the function calls the Supabase Admin API (`auth.admin.generateLink`, type `magiclink`) for that barber's `auth_user_id`, then immediately exchanges the resulting token server-side (`verifyOtp`) to obtain a real access/refresh token pair, and returns those tokens to the station app — which stores them exactly as it would for a password login.
4. The barber's `staff_users.pin_hash` is set once, by a Branch Manager or Owner from Barbers Management (App Flow section 8.9) — not Staff & Roles (8.12), which is Owner-only and handles account creation, not this barber-specific operational step (section 3.4) — and can be rotated the same way; it is never visible in plaintext after creation.

This means "End Shift" on a shared station (App Flow section 9.4) is an ordinary Supabase sign-out — no separate session model to maintain.

### 3.4 Staff Invitation and Account Creation

Per PRD section 46, every staff account except the first Owner (created via the one-time manual bootstrap in PRD section 46.1) originates from an invite. This adds one enum and four columns to `staff_users` — no new table, since an invite is a transient state of a staff account, not a separate entity with its own lifecycle:

```sql
create type staff_invite_status as enum ('pending','accepted','revoked','expired');

alter table staff_users
  add column invite_status      staff_invite_status not null default 'accepted', -- the bootstrap Owner is created already-accepted
  add column invited_by_staff_id uuid references staff_users(id),                -- null only for the bootstrap Owner
  add column invited_at         timestamptz,
  add column invite_accepted_at timestamptz;

create index idx_staff_users_invite_status on staff_users(invite_status) where invite_status = 'pending';
```

The invite/acceptance flow reuses the exact same Admin-API pattern as barber PIN login (section 3.3), rather than inventing a second way to turn an identity into a live session:

1. Owner submits the Invite Staff form (App Flow section 8.12): name, role, branch, and a phone number or email. A service-role Edge Function (`staff-invite`) calls `auth.admin.createUser` for that contact method with no password set, creates the corresponding `staff_users` row with `invite_status = 'pending'`, `invited_by_staff_id` set to the Owner's `staff_users.id`, and `invited_at = now()`, then calls `auth.admin.generateLink` (type `invite`) and sends the resulting link by SMS or email depending on which contact method was given.
2. The invitee opens the link, which lands on Accept Staff Invite (App Flow section 8.15) with no prior session. That screen's submit calls a second service-role Edge Function (`staff-invite-accept`) that server-side exchanges the invite token (`verifyOtp`), then calls `auth.admin.updateUser` with the password the invitee just chose, and finally updates that `staff_users` row to `invite_status = 'accepted'` and `invite_accepted_at = now()`. From that point the account behaves like any other, and logs in normally through the flow in section 3.2.
3. **Resend** (App Flow 8.12) re-runs step 1's `generateLink` call against the same `staff_users` row without creating a new one. **Revoke** sets `invite_status = 'revoked'`; a revoked or expired invite's link fails at step 2 with the "no longer valid" state App Flow section 8.15 describes, and a revoked account cannot be un-revoked back into `pending` — a fresh invite is sent instead, which is simpler than reasoning about a re-activated stale token.

Client applications never call `createUser`, `generateLink`, `updateUser`, or `verifyOtp` directly against staff identities — both Edge Functions run under the service-role key, exactly like `pin-login` in section 3.3, so this stays a server-side-only capability regardless of what any client bundle exposes.

### 3.5 Biometric (Passkey) Quick Login

Per PRD section 47, this adds **no new table and no new column** to either `customers` or `staff_users` — a deliberate outcome, not an oversight. Supabase Auth's native passkey/WebAuthn support (tech stack document section 23) manages enrolled credentials entirely inside its own internal tables, keyed against the same `auth.users.id` every `customers`/`staff_users` row already references via `auth_user_id`. A passkey is, from this schema's point of view, just another way the same `auth.users` row gets authenticated — nothing downstream changes: `custom_access_token_hook` (section 3.2) runs exactly the same way regardless of whether the session in front of it came from a password, an OTP, or a passkey ceremony, so every RLS policy in section 14 and every helper function (`auth_role()`, `has_capability()`, `in_branch_scope()`) needs zero changes for this feature.

This is also why, unlike barber PIN login (section 3.3) and staff invitation (section 3.4), **no custom Edge Function is needed** for the personal-device case: a PIN and an invite token are both bespoke mechanisms this schema had to build the token-exchange plumbing for (`generateLink` + `verifyOtp`, run server-side under the service-role key), whereas a passkey is a WebAuthn ceremony Supabase Auth's own client SDK already knows how to run end-to-end (`supabase.auth.registerPasskey()` / `signInWithPasskey()`, tech stack section 23) — the enrollment and sign-in calls go directly from the client to Supabase Auth, with no Pixel Barber server code sitting in between.

The one place this schema does touch the feature is the shared-station barber case (PRD section 47.4), and only procedurally, not structurally: a barber enrolls a station's fingerprint sensor by calling `registerPasskey()` while already holding a valid session from that station's existing PIN login (section 3.3) — enrollment requires an authenticated user, exactly as Supabase's passkey support requires, so PIN login (or a personal-device login) is always what gets a barber to the point of being able to enroll a station passkey in the first place, never the other way around. Signing in afterward via the sensor calls `signInWithPasskey()`'s discoverable-credential flow directly from the station app, which resolves to whichever barber's enrolled credential matches and mints a session for that `auth.users` row the same way `pin-login`'s `verifyOtp` exchange does today — two different mechanisms arriving at the same kind of session, which is exactly why nothing else in this document needs to know or care which one was used.

No endpoint is added to section 17's table for this feature, for the same reason: there is no server-side step of Pixel Barber's own to document — see that section's note.

```sql
create table businesses (
  id                uuid primary key default gen_random_uuid(),
  name              text not null,

create unique index one_business_only on businesses ((true));
```

```sql
create type branch_status as enum ('open','closed','closing_soon','temporarily_closed');

create table branches (
  id                 uuid primary key default gen_random_uuid(),
  business_id        uuid not null references businesses(id),
  name               text not null,
  branch_code        text not null unique,          -- short code used in ticket numbers, e.g. 'OSU'
  address            text not null,
  latitude           numeric(9,6) not null,
  longitude          numeric(9,6) not null,
  phone_e164         text,

);

```

`branch_status` itself is not a stored column — "Open / Closed / Closing Soon" is a function of `branch_hours`, `branch_closures`, and `is_temporarily_closed` evaluated against the current time, computed by a view (section 4.1) rather than duplicated as data that could drift from the hours it's derived from.

```sql
create table branch_hours (
  id          uuid primary key default gen_random_uuid(),
  branch_id   uuid not null references branches(id) on delete cascade,
  day_of_week smallint not null check (day_of_week between 0 and 6),  -- 0 = Sunday
  opens_at    time,
  closes_at   time,
  is_closed   boolean not null default false,
  unique (branch_id, day_of_week)
);

create table branch_closures (
  id           uuid primary key default gen_random_uuid(),
  branch_id    uuid not null references branches(id) on delete cascade,
  closure_date date not null,
  reason       text,
  unique (branch_id, closure_date)
);
```

### 4.1 Derived branch status view

```sql
create view branch_status_view as
select
  b.id as branch_id,
  case
    when b.is_temporarily_closed then 'temporarily_closed'
    when bc.branch_id is not null then 'closed'
    when bh.is_closed or bh.id is null then 'closed'
    when now()::time between bh.opens_at and bh.closes_at - interval '30 minutes' then 'open'
    when now()::time between bh.closes_at - interval '30 minutes' and bh.closes_at then 'closing_soon'
    else 'closed'
  end::branch_status as status
from branches b
left join branch_closures bc on bc.branch_id = b.id and bc.closure_date = current_date
left join branch_hours bh on bh.branch_id = b.id and bh.day_of_week = extract(dow from now())::smallint;
```

The 30-minute "closing soon" window is a reasonable default matching the PRD's intent (section 11: branch status must always be visible before a customer attempts to join) — expose it as a per-branch configurable value later if a branch wants a different threshold; it isn't worth its own column until that need is real.

## 5. Services and Pricing

```sql
create table services (
  id                      uuid primary key default gen_random_uuid(),
  business_id             uuid not null references businesses(id),
  name                    text not null,
  description             text,
  category                text,
  default_duration_minutes smallint not null,
  image_url               text,
  is_active               boolean not null default true,
  created_at              timestamptz not null default now(),
  updated_at              timestamptz not null default now()
);
create trigger trg_services_updated_at before update on services
  for each row execute function set_updated_at();
```

```sql
create table branch_services (
  id                       uuid primary key default gen_random_uuid(),
  branch_id                uuid not null references branches(id) on delete cascade,
  service_id               uuid not null references services(id),
  duration_minutes_override smallint,     -- null = use services.default_duration_minutes
  is_active                boolean not null default true,
  created_at               timestamptz not null default now(),
  updated_at               timestamptz not null default now(),
  unique (branch_id, service_id)
);
create trigger trg_branch_services_updated_at before update on branch_services
  for each row execute function set_updated_at();
```

Pricing is effective-dated (PRD section 10: "business-wide default with a branch-specific override and an effective date for changes, plus an optional promotional price"), so it's its own append-only-ish table rather than two columns on `branch_services` that would silently lose history on every price change:

```sql
create table branch_service_prices (
  id                uuid primary key default gen_random_uuid(),
  branch_service_id uuid not null references branch_services(id) on delete cascade,
  price_ghs         numeric(10,2) not null check (price_ghs >= 0),
  is_promo          boolean not null default false,
  effective_from    date not null,
  effective_until   date,                 -- null = open-ended, superseded implicitly by a later row
  created_at        timestamptz not null default now()
);
create index idx_branch_service_prices_lookup
  on branch_service_prices(branch_service_id, effective_from desc);
```

"The price that currently applies" is a query (promo row, if one is active today, otherwise the latest non-promo row with `effective_from <= current_date` and `effective_until` null or in the future) rather than a flag maintained by the application — expressed once as a view:

```sql
create view current_branch_service_price as
select distinct on (branch_service_id)
  branch_service_id, price_ghs, is_promo
from branch_service_prices
where effective_from <= current_date
  and (effective_until is null or effective_until >= current_date)
order by branch_service_id, is_promo desc, effective_from desc;
```

Barber eligibility per service (PRD section 10: "which barbers are eligible to perform it") is modeled from the barber side, since the PRD also describes it as part of a barber's profile (section 15: "the services they're skilled and authorized to perform") — one fact, one table, referenced from both directions rather than duplicated:

```sql
create table barber_skills (
  barber_id  uuid not null references barbers(id) on delete cascade,
  service_id uuid not null references services(id) on delete cascade,
  primary key (barber_id, service_id)
);
```

## 6. Barbers and Scheduling

```sql
create type barber_status as enum
  ('offline','scheduled','available','busy','on_break','temporarily_unavailable','end_of_shift');

create table barbers (
  id                 uuid primary key default gen_random_uuid(),
  staff_user_id      uuid not null unique references staff_users(id) on delete cascade,
  home_branch_id     uuid not null references branches(id),
  status             barber_status not null default 'offline',
  average_rating     numeric(3,2),               -- denormalized from feedback (section 15.4) for fast dashboard reads
  current_ticket_id  uuid references queue_tickets(id),
  created_at         timestamptz not null default now(),
  updated_at         timestamptz not null default now()
);
create trigger trg_barbers_updated_at before update on barbers
  for each row execute function set_updated_at();
```

"Today's branch, if floating" (PRD section 15) is a schedule fact, not a barber property, so it lives in `barber_schedule`, keyed by date — a barber with no row for today is simply working their `home_branch_id`:

```sql
create table barber_schedule (
  id           uuid primary key default gen_random_uuid(),
  barber_id    uuid not null references barbers(id) on delete cascade,
  work_date    date not null,
  branch_id    uuid not null references branches(id),   -- home branch unless floating that day
  shift_start  time not null,
  shift_end    time not null,
  break_start  time,
  break_end    time,
  unique (barber_id, work_date)
);
```

Per-barber, per-service historical average duration (PRD section 17: "where a barber has enough completed-service history... their own historical average should be used") is a maintained rollup, not a live aggregation over every `service_sessions` row on every wait-time calculation — see section 15.4 for the trigger that keeps it current:

```sql
create table barber_service_stats (
  barber_id             uuid not null references barbers(id) on delete cascade,

  completed_count       integer not null default 0,
  avg_duration_seconds  integer,   -- null until completed_count reaches a minimum sample size (app-level threshold)
  updated_at            timestamptz not null default now(),
  primary key (barber_id, service_id)
);
```

Staff branch assignment (many-to-many, since a Branch Manager or Receptionist can be assigned to more than one branch):

```sql

  branch_id     uuid not null references branches(id) on delete cascade,
  primary key (staff_user_id, branch_id)

```

A barber's own assignment is implied by `barbers.home_branch_id` plus any `barber_schedule` row, so barbers don't also need rows here — this table is for non-barber staff roles, whose branch access isn't already expressed elsewhere.

## 13. Customer Segmentation (View, Not a Table)

PRD section 28 asks for segments (new, returning, frequent, dormant, at-risk) "with segmentation logic kept transparent rather than a black box." A view computed from data that already exists is the most transparent form that logic can take — anyone can read the exact rule by reading the view definition, and there's no separate table that can silently drift out of sync with the tickets it's summarizing:

```sql
create view customer_segments as
select
  c.id as customer_id,
  count(qt.id) filter (where qt.state = 'completed') as completed_visits,
  max(qt.completed_at) as last_visit_at,
  case
    when count(qt.id) filter (where qt.state = 'completed') = 0 then 'new'
    when max(qt.completed_at) < now() - interval '90 days' then 'dormant'
    when c.no_show_count >= 3 or c.late_cancellation_count >= 3 then 'at_risk'
    when count(qt.id) filter (where qt.state = 'completed' and qt.completed_at > now() - interval '90 days') >= 3 then 'frequent'
    else 'returning'
  end as segment
from customers c
left join queue_tickets qt on qt.customer_id = c.id
where c.is_anonymized = false
group by c.id;
```

The exact thresholds (90 days, 3 visits, 3 no-shows) are illustrative defaults matching the PRD's own descriptive language ("dormant," "frequent," "at-risk") — move them into `businesses.default_policies` and reference that from the view the moment the business wants them configurable, rather than a code change.

## 14. Row-Level Security

### 14.1 Principles

RLS is enabled on every table in this document (`alter table … enable row level security`), with no exceptions — PRD section 32's "enforced server-side, not just hidden in the UI" and section 33's data-protection framing both mean the database itself is the enforcement point, not application code that could be bypassed by calling PostgREST directly. Four shapes cover nearly every table:

**Public read-only reference data** (branches, branch_hours, branch_closures, services, branch_services, branch_service_prices, barbers, barber_skills) — anyone, including an unauthenticated visitor browsing Branch Discovery (App Flow section 4.2) before creating an account, can `SELECT`; only staff with the relevant capability can write.

**Customer-owned data** (customers, queue_tickets, appointments, feedback, push_subscriptions, consents, notifications where `recipient_type = 'customer'`) — a customer can `SELECT`/write their own rows (matched via `customers.auth_user_id = auth.uid()`); staff can `SELECT`/write rows in their branch scope; nobody can read across customers or across branches without the Owner's branch-agnostic access.

**Staff-internal operational data** (barber_schedule, barber_service_stats, audit_log, queue_events) — no customer access at all; staff access follows capability + branch scope.

**Append-only logs** (queue_events, audit_log, consents) — `INSERT` allowed per the above; `UPDATE`/`DELETE` revoked outright (section 12), which is a stronger guarantee than an RLS policy that merely returns no rows.

### 14.2 Representative policies

```sql
alter table branches enable row level security;
create policy branches_public_read on branches for select using (true);
create policy branches_staff_write on branches for all
  using (has_capability('manage_branches') and in_branch_scope(id))
  with check (has_capability('manage_branches') and in_branch_scope(id));
```

```sql
alter table customers enable row level security;

create policy customers_self_read on customers for select
  using (auth_user_id = auth.uid());

create policy customers_self_update on customers for update
  using (auth_user_id = auth.uid())
  with check (auth_user_id = auth.uid());

-- Staff can see/edit any customer who has an active or historical ticket at a branch
-- in their scope (Owner sees everyone) — this is what powers the CRM (App Flow 8.10)
-- without giving staff blanket access to every customer in the business regardless of branch.
create policy customers_staff_scoped on customers for select
  using (
    auth_role() = 'owner'
    or exists (
      select 1 from queue_tickets qt
      where qt.customer_id = customers.id and qt.branch_id = any(auth_branch_ids())
    )
  );

create policy customers_staff_register_walkin on customers for insert
  with check (has_capability('register_walkins'));
```

```sql
alter table staff_users enable row level security;

-- but never their own role, invite_status, or pin_hash, which is why the
-- with check below is narrower than a blanket "own row" policy would be.
create policy staff_users_self_read on staff_users for select
  using (auth_user_id = auth.uid());

create policy staff_users_self_update_profile on staff_users for update
  using (auth_user_id = auth.uid())
  with check (auth_user_id = auth.uid());
-- Enforced alongside this policy, not instead of it: a trigger (or column-level

```

## 15. Scheduled and Trigger-Driven Logic

### 15.1 Ticket number generation

Atomic per-branch, per-day sequence, reset daily (PRD section 12.2), using an upsert rather than a Postgres `SEQUENCE` object (which can't easily reset per branch per day on its own):

```sql
create or replace function next_ticket_number(p_branch_id uuid) returns text
language plpgsql as $$
declare
  v_code text;
  v_seq  integer;
begin
  select branch_code into v_code from branches where id = p_branch_id;

  insert into branch_ticket_counters (branch_id, ticket_date, last_seq)
    values (p_branch_id, current_date, 1)
  on conflict (branch_id, ticket_date)
    do update set last_seq = branch_ticket_counters.last_seq + 1
  returning last_seq into v_seq;

  return format('PB-%s-%s', v_code, v_seq);
end;
$$;
```

Called from the ticket-creation path (whichever server action or Edge Function handles Join Queue / Add Walk-in / appointment conversion) before the `insert` into `queue_tickets`, so `ticket_number` is always supplied, never generated by a default expression that would be harder to make branch-and-day-aware in plain SQL.

### 15.2 Queue position

`queue_tickets.position` is a cache, refreshed by a trigger whenever a ticket in a given branch/barber-pool changes state, rather than computed fresh on every read (App Flow section 7.6 needs this on a live, frequently-polled/subscribed screen):

```sql
create or replace function recalculate_positions(p_branch_id uuid, p_barber_id uuid) returns void
language plpgsql as $$
begin
  with ranked as (
    select id, row_number() over (order by created_at) as rn
    from queue_tickets
    where branch_id = p_branch_id
      and state in ('waiting','almost_turn')
      and (p_barber_id is null or assigned_barber_id = p_barber_id or (assigned_barber_id is null and is_pooled))
  )
  update queue_tickets qt set position = ranked.rn
  from ranked where qt.id = ranked.id;
end;
$$;

create or replace function trg_ticket_state_changed() returns trigger
language plpgsql as $$
begin
  if new.state is distinct from old.state then
    perform recalculate_positions(new.branch_id, new.assigned_barber_id);
  end if;
  return new;
end;
$$;

create trigger after_ticket_state_change after update of state on queue_tickets
  for each row execute function trg_ticket_state_changed();
```

The actual wait-time *estimate* (`estimated_wait_low_min`/`high_min`) is intentionally left for application/Edge Function logic to compute and write, not a trigger — PRD section 17's formula depends on the currently-in-service ticket's live elapsed time (a moving target that a state-change trigger alone won't recompute every second) and on `barber_service_stats`/`services.default_duration_minutes`, which is a calculation better expressed in TypeScript alongside the rest of the notification/recalculation logic than as a second, parallel SQL implementation of the same formula.

### 15.3 Grace-period expiry and appointment activation (`pg_cron`)

```sql
select cron.schedule(
  'expire-no-show-grace-periods',
  'every 30 seconds',   -- Supabase's pg_cron accepts standard cron syntax; a 30s cadence keeps the released-ticket
                         -- notification (PRD 21) close to the actual 2-minute deadline without a dedicated worker
  $$
  update queue_tickets
    set state = 'no_show', no_show_at = now()
    where state in ('called','grace_period')
      and grace_period_expires_at < now();
  $$
);

select cron.schedule(
  'activate-due-appointments',
  '* * * * *',   -- every minute
  $$
  with due as (
    select a.* from appointments a
    where a.status = 'scheduled' and a.scheduled_start <= now() + interval '5 minutes'
  ),
  created as (
    insert into queue_tickets (
      ticket_number, branch_id, customer_id, branch_service_id, preferred_barber_id,
      appointment_id, state, created_by
    )
    select
      next_ticket_number(due.branch_id), due.branch_id, due.customer_id, due.branch_service_id,
      due.preferred_barber_id, due.id, 'waiting', 'appointment_conversion'
    from due
    returning appointment_id
  )
  update appointments set status = 'converted'
    where id in (select appointment_id from created);
  $$
);
```

An actual production version of the first job also needs to write the resulting `queue_events` row and enqueue the "your ticket was released" notification for each affected ticket — shown here as the state transition alone for clarity; wrap both jobs' bodies in a single `plpgsql` function per job (rather than inline SQL, as above) once that additional work is added, so the cron schedule definition itself stays a one-line reference to a named function.

### 15.4 Keeping `barber_service_stats` and `barbers.average_rating` current

```sql
create or replace function trg_service_session_completed() returns trigger
language plpgsql as $$
declare
  v_service_id uuid;
begin
  if new.ended_at is not null and old.ended_at is null then
    select branch_service_id into v_service_id from queue_tickets where id = new.ticket_id;
    insert into barber_service_stats (barber_id, service_id, completed_count, avg_duration_seconds)
      select new.barber_id, bs.service_id, 1, new.actual_duration_seconds
      from branch_services bs where bs.id = v_service_id
    on conflict (barber_id, service_id) do update set
      avg_duration_seconds = (
        (barber_service_stats.avg_duration_seconds * barber_service_stats.completed_count + new.actual_duration_seconds)
        / (barber_service_stats.completed_count + 1)
      ),
      completed_count = barber_service_stats.completed_count + 1,
      updated_at = now();
  end if;
  return new;
end;
$$;

create trigger after_service_session_update after update on service_sessions
  for each row execute function trg_service_session_completed();
```

`barbers.average_rating` is refreshed the same way, off a trigger on `feedback` insert (`avg(overall_rating) over that barber`, written into `barbers.average_rating` so the Staff Operations Dashboard's barber cards — App Flow section 8.5 — read one column instead of aggregating on every dashboard load).

## 16. Realtime

Every screen the App Flow document marks "live" (section 3: "updates via the same real-time channel... without a manual refresh") subscribes to Postgres Changes on the relevant table, which Supabase filters through the same RLS policies as an ordinary query — a customer's Realtime subscription to `queue_tickets` only ever receives changes to rows their `customers_self_*`/`tickets_customer_own` policies would let them `SELECT` directly, so there's no separate Realtime-specific authorization layer to design.

```sql
alter publication supabase_realtime add table
  queue_tickets, appointments, barbers, notifications, branches;
```

`queue_events` and `audit_log` are deliberately **not** added to this publication — they're read on demand (reporting, dispute resolution) rather than watched live, and excluding them keeps the realtime replication stream focused on what the UI actually needs to update without a refresh.

## 17. Custom API Endpoints

Standard CRUD (reading branches, listing a customer's own tickets, updating a profile field) goes through the Supabase client directly against PostgREST, protected by the RLS policies in section 14 — nothing below duplicates that. What follows is only the logic that genuinely needs a server-side step: a third-party call, a privileged operation, or multi-table work that must be atomic. Each is a Supabase Edge Function unless noted, per the tech stack document's decision to keep this logic out of either Next.js app.

| Endpoint | Method | Purpose | Notes |
|---|---|---|---|
| `/auth/otp/send` | POST | Send the signup/password-reset OTP (App Flow 5.2) | Thin wrapper that triggers Supabase Auth's built-in phone-OTP flow — included here only because the phone number must be validated/normalized to E.164 (PRD 9.2) before Supabase Auth ever sees it. SMS delivery for this flow is MessageBird, configured natively in the Supabase project's Auth settings (MessageBird is one of Auth's supported OTP providers) — no custom Edge Function or Auth Hook needed for this path |
| `/auth/pin-login` | POST | Barber shared-station PIN login | Section 3.3 in full — the one auth path that isn't a direct Supabase Auth client call |
| `/tickets/walk-in` | POST | Staff "Add Walk-in" (App Flow 8.6) | Creates or matches a `customers` row by phone (section 2), calls `next_ticket_number`, inserts the `queue_tickets` row, writes the `queue_events` row, and enqueues the SMS confirmation — one atomic function rather than four separate client calls that could partially fail |

| `/maps/travel-time` | POST | Server-side Distance Matrix proxy (tech stack section 11) | Keeps `GOOGLE_MAPS_SERVER_API_KEY` off the client; the customer app calls this instead of Google's REST API directly |
| `/staff/broadcast` | POST | Segment broadcast (App Flow 8.11) | Resolves the segment (section 13's view) to a customer list, checks `consents` for `marketing` per recipient, and fans out through the notification tables — a plain Next.js server action with the service-role key is sufficient here, since it's staff-triggered rather than needing Edge Function isolation |

## 18. Retention and Erasure

Per the locked 3-year-from-last-activity retention decision: a `pg_cron` job (monthly is frequent enough for a retention sweep, unlike the sub-minute jobs in section 15.3) finds `customers` rows where `last_activity_at < now() - interval '3 years'` and `is_anonymized = false`, and anonymizes rather than deletes them — overwriting `name`, `phone_e164`, and `email` with placeholder values, clearing `auth_user_id` (after also deleting the corresponding `auth.users` row via the Admin API, which a plain SQL job can't do itself — this job flags candidates, and a paired Edge Function does the actual `auth.users` deletion and the anonymizing `UPDATE` together, keeping both in one place), and setting `is_anonymized = true` / `anonymized_at = now()`. Every `queue_tickets`, `feedback`, `queue_events`, and `service_sessions` row tied to that customer is left in place — they carry `customer_id`, which after this process points at a row with no identifying information left on it — so historical KPIs and reports (PRD sections 30–31) stay numerically accurate indefinitely, exactly matching the "anonymize, keep aggregate history" decision.

`last_activity_at` is bumped (a small trigger on `queue_tickets`/`appointments` insert, keyed by `customer_id`) every time a customer joins a queue, books, or logs in — so the 3-year clock is genuinely "since last activity," not "since account creation."

A customer-initiated deletion request (PRD section 33: "a real way to request their data be deleted") runs the same anonymization function immediately, on demand, rather than waiting for the scheduled sweep — one function, two triggers (a cron schedule and a direct staff/support-tool call), never two implementations of "what deletion means" to keep consistent with each other.

## 19. Migration and Naming Conventions

Supabase CLI migrations live in `supabase/migrations/`, one timestamped file per logical change (`20260909120000_create_businesses_and_branches.sql`, etc.) — per the tech stack document's decision to document schema narratively rather than ship ready-to-run files from this document itself, the SQL above is the reference an engineer copies into those migration files in roughly the section order given (identity and RBAC tables before anything that references them, reference data before the tables that join against it, `queue_tickets`/`appointments` after both, triggers and RLS policies after their tables exist). Every enum, table, and function name in this document is final and should be used verbatim in migrations rather than re-invented per-implementer, so that this document and the eventual codebase never drift into two different vocabularies for the same thing.

## 20. What Later Phases Will Add on Top of This

Per the decisions locked at the top of this document, none of the following required any schema footprint in v1, but each has an obvious, non-disruptive landing spot when its PRD-section-43 decision is revisited: cross-branch transfer adds a nullable `transferred_from_ticket_id` self-reference on `queue_tickets`; a VIP/loyalty tier adds a nullable `tier` column on `customers`; enforcing the no-show consequence policy starts reading the already-present `requires_confirmation_call` flag from wherever ticket-calling logic lives, rather than adding it retroactively; and a real per-branch queue cap starts being checked at ticket-creation time against the already-present `branches.max_queue_size`, rather than that column needing to be added then. ### 21.2 Conversations and Messages

```sql
create type conversation_status as enum ('active','read_only','anonymized');

create table conversations (
  id              uuid primary key default gen_random_uuid(),
  queue_ticket_id uuid references queue_tickets(id),
  appointment_id  uuid references appointments(id),
  customer_id     uuid not null references customers(id),
  barber_id       uuid not null references barbers(id),
  status          conversation_status not null default 'active',
  closed_at       timestamptz,
  anonymized_at   timestamptz,
  created_at      timestamptz not null default now(),
  check (queue_ticket_id is not null or appointment_id is not null)
);

-- A reassignment closes the old conversation and opens a new one (PRD 45.4) rather than ever
-- having two simultaneously active conversations for the same ticket or appointment.
create unique index one_active_conversation_per_ticket
  on conversations (queue_ticket_id) where status = 'active' and queue_ticket_id is not null;
create unique index one_active_conversation_per_appointment
  on conversations (appointment_id) where status = 'active' and appointment_id is not null;
create index idx_conversations_customer on conversations(customer_id);
create index idx_conversations_barber on conversations(barber_id);
```

```sql
create type message_sender_type as enum ('customer','barber');
create type message_type as enum ('text','voice_note','quick_reply');

create table messages (
  id                          uuid primary key default gen_random_uuid(),
  conversation_id             uuid not null references conversations(id) on delete cascade,
  sender_type                 message_sender_type not null,
  sender_id                   uuid not null,   -- customers.id or barbers.id, per sender_type
  message_type                message_type not null default 'text',
  body                        text,            -- text content, or the quick-reply's canned string
  voice_note_storage_path     text,            -- Supabase Storage object path, when message_type = 'voice_note'
  voice_note_duration_seconds smallint check (voice_note_duration_seconds is null or voice_note_duration_seconds <= 60),
  delivered_at                timestamptz,
  read_at                     timestamptz,
  created_at                  timestamptz not null default now(),
  check (
    (message_type = 'voice_note' and voice_note_storage_path is not null)
    or (message_type in ('text','quick_reply') and body is not null)
  )
);
create index idx_messages_conversation on messages(conversation_id, created_at);
```

The four quick-reply strings (PRD section 45.2) are not a database table — they're seeded as `next-intl` translation keys, the same as every other fixed UI string in the app (Implementation Plan Phase 2's i18n scaffolding), since the PRD treats them as a fixed, product-defined set rather than something a business configures per branch.

### 21.3 Lifecycle Trigger — Closing a Conversation

A conversation never decides its own lifecycle — `queue_tickets` and `appointments` drive it, exactly as PRD section 45.4 describes:

```sql
create or replace function close_conversation_on_ticket_end() returns trigger
language plpgsql as $$
begin
  if new.state in ('completed','cancelled','no_show') and old.state is distinct from new.state then
    update conversations set status = 'read_only', closed_at = now()
      where queue_ticket_id = new.id and status = 'active';
  end if;
  return new;
end;
$$;
create trigger after_ticket_end after update of state on queue_tickets
  for each row execute function close_conversation_on_ticket_end();

create or replace function close_conversation_on_appointment_end() returns trigger
language plpgsql as $$
begin
  if new.status in ('completed','cancelled','no_show') and old.status is distinct from new.status then
    update conversations set status = 'read_only', closed_at = now()
      where appointment_id = new.id and status = 'active';
  end if;
  return new;
end;
$$;
create trigger after_appointment_end after update of status on appointments
  for each row execute function close_conversation_on_appointment_end();

-- Barber reassignment (PRD 16/45.4): the old conversation closes, a new one opens with the new barber.
create or replace function close_conversation_on_reassignment() returns trigger
language plpgsql as $$
begin
  if new.assigned_barber_id is distinct from old.assigned_barber_id then
    update conversations set status = 'read_only', closed_at = now()
      where queue_ticket_id = new.id and status = 'active';
    if new.assigned_barber_id is not null then
      insert into conversations (queue_ticket_id, customer_id, barber_id)
        values (new.id, new.customer_id, new.assigned_barber_id);
    end if;
  end if;
  return new;
end;
$$;
create trigger after_ticket_reassigned after update of assigned_barber_id on queue_tickets
  for each row execute function close_conversation_on_reassignment();
```

### 21.4 Retention — 30-Day Anonymization

Parallel to section 18's 3-year customer anonymization job, but on its own, much shorter clock, since a conversation's sensitivity is tied to one visit, not an account's whole history:

```sql
select cron.schedule(
  'anonymize-closed-conversations',
  '0 3 * * *',  -- once a day
  $$
  update messages set body = null, voice_note_storage_path = null
    where conversation_id in (
      select id from conversations
      where status = 'read_only' and closed_at < now() - interval '30 days'
    );
  update conversations set status = 'anonymized', anonymized_at = now()
    where status = 'read_only' and closed_at < now() - interval '30 days';
  $$
);
```

Deleting the underlying Storage object for a voice note (not just the database's pointer to it) needs the Storage Admin API, which plain SQL can't call — pair this job with a small Edge Function on the same schedule that reads `voice_note_storage_path` before it's nulled and deletes the object, the same pairing pattern section 18 uses for `auth.users` deletion alongside customer anonymization.

### 21.5 The Audited Content-Access Path

Per PRD section 45.5, staff never get a direct `SELECT` policy on `messages.body`/`voice_note_storage_path` — content is only ever reached through one `SECURITY DEFINER` function that logs its own use:

```sql
create table conversation_content_access_log (
  id              uuid primary key default gen_random_uuid(),
  conversation_id uuid not null references conversations(id),
  staff_user_id   uuid not null references staff_users(id),
  reason          text not null,
  accessed_at     timestamptz not null default now()
);

create or replace function staff_view_conversation(p_conversation_id uuid, p_reason text)
returns setof messages
language plpgsql
security definer
as $$
declare
  v_branch_id uuid;
begin
  select coalesce(qt.branch_id, a.branch_id) into v_branch_id
    from conversations c
    left join queue_tickets qt on qt.id = c.queue_ticket_id
    left join appointments a on a.id = c.appointment_id
    where c.id = p_conversation_id;

  if not (has_capability('view_message_content') and in_branch_scope(v_branch_id)) then
    raise exception 'not authorized to view message content';
  end if;

  insert into conversation_content_access_log (conversation_id, staff_user_id, reason)
    values (p_conversation_id, auth_staff_id(), p_reason);

  return query select * from messages where conversation_id = p_conversation_id order by created_at;
end;
$$;
```

Add `view_message_content` to the `capabilities` table (section 3.1) and assign it only to `branch_manager` and `owner` in `role_capabilities`, per PRD section 32's Phase 2 addition.

### 21.6 RLS

```sql
alter table conversations enable row level security;
alter table messages enable row level security;
alter table conversation_content_access_log enable row level security;

  using (customer_id in (select id from customers where auth_user_id = auth.uid()));

  using (barber_id = (select id from barbers where staff_user_id = auth_staff_id()));

create policy conversations_staff_metadata on conversations for select
  using (
    in_branch_scope(coalesce(
      (select branch_id from queue_tickets where id = conversations.queue_ticket_id),
      (select branch_id from appointments where id = conversations.appointment_id)
    ))
  );

create policy messages_participants_read on messages for select
  using (
    conversation_id in (
      select id from conversations
      where customer_id in (select id from customers where auth_user_id = auth.uid())
         or barber_id = (select id from barbers where staff_user_id = auth_staff_id())
    )
  );

create policy messages_participants_send on messages for insert
  with check (
    conversation_id in (
      select id from conversations c
      where c.status = 'active'
        and (
          c.customer_id in (select id from customers where auth_user_id = auth.uid())
          or c.barber_id = (select id from barbers where staff_user_id = auth_staff_id())
        )
    )
  );
-- Deliberately no staff select/insert policy on messages at all: content only ever reaches a
```
