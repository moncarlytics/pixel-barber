# Pixel Barber — Implementation Plan, Phase 2

**Document status:** Execution plan — the sequence Claude Code follows to build PRD Phase 2 on top of the deployed MVP
**Version:** 1.0
**Date:** 10 September 2026
**Companion to:** `pixel-barber-prd.md` (sections 18, 25, 28, 30–31, 39, 43, 45, 47 in particular), `pixel-barber-app-flow.md`, `pixel-barber-tech-stack.md` (its section 23 especially, for Phase 15), `pixel-barber-backend-schema.md` (its Phase 2 addendum in section 21, and sections 3.4–3.5, especially), `pixel-barber-design-system.md`, and `pixel-barber-implementation-plan.md` — this document picks up exactly where that last one's Phase 10 ends and does not repeat anything already built there.

**Decisions locked for this plan**, from the clarifying round before it was written: the plan starts from **what's genuinely still unbuilt**, not from a literal restatement of PRD section 39's Phase 2 list — two items on that list, location-based travel-time/geofencing and historical barber-duration learning, were already fully built during the MVP plan's Phases 4, 5, and 7, because the MVP queue and wait-time engine genuinely needed them to work as PRD sections 17 and 19 specify; the base CRM segmentation view and reporting dashboards from MVP Phase 8 exist too, even though "richer CRM" and "fuller reporting" are nominally Phase 2 language. Section 0 below states exactly what that means for scope. Cross-branch ticket transfer — the one item PRD section 43 left genuinely open and the Backend Schema document gave zero schema footprint on purpose — **is being built now**, resolving that open decision. Biometric (fingerprint/face) quick login (PRD section 47) was added to this plan's scope after it was first written, from its own clarifying round: quick re-login only (never a passwordless-only account model) for both customer and staff personal devices, added alongside — never replacing — the barber shared-station PIN login. Phases in this document **continue the first plan's numbering**, starting at Phase 11, reflecting one continuous build rather than a second, independent sequence. Scope **stops at PRD Phase 2**; PRD Phase 3's predictive/conversational AI direction stays out of scope here for the same reason the PRD itself gives it no detailed spec yet (PRD section 27).

Every convention the first plan established carries forward unchanged: vertical slices (each phase spans backend, customer app, and staff app together), tests written alongside each phase rather than retrofitted, continuous execution with stops only for genuine blockers, and — since staging and production are already live from Phase 0 — every phase here deploys to that same running production environment rather than standing up anything new.

## 0. What's Already Done, and What This Plan Actually Covers

PRD section 39 lists five items under "Phase 2." Two of them are already in production: location-based travel-time and geofencing (PRD section 19) shipped as part of the first plan's Phase 7, and historical barber/service-duration learning feeding the wait-time estimate (PRD section 17) shipped as part of Phases 4 and 5 — both were load-bearing parts of making the MVP's own core queue experience work correctly, not optional extras, so building the MVP properly meant building them. A third, CRM segmentation and reporting (PRD sections 28, 30–31), also has a real baseline in production from Phase 8 — the `customer_segments` view, Reports, and the Business-Wide Dashboard all exist and work. This plan does not re-build any of that.

What this plan actually sequences is five things: cross-branch ticket transfer (PRD section 25, resolving PRD section 43's last open item); in-app customer–barber messaging (PRD section 45); the expanded, build-your-own avatar personalization and animation system (PRD section 18's Phase 2 enhancement); a phase that takes the existing CRM/reporting baseline from "works" to what PRD sections 28 and 31 actually ask for beyond that baseline — configurable segmentation and real revenue/KPI depth, not a rebuild; and biometric (fingerprint/face) quick login (PRD section 47), added last, on top of every other login path this plan and the first plan already built.

## 1. Phase 11 — Cross-Branch Ticket Transfer

**Builds on:** the first plan's Phase 4 (queue engine), Phase 2 (branch data and comparison), and Backend Schema section 20's already-planned landing spot for this feature.

**Scope.** Add the schema section 20 flagged as the non-disruptive addition for this decision: a nullable `transferred_from_ticket_id` self-reference on `queue_tickets`, plus a per-branch `allow_cross_branch_transfer` boolean (default `false`) on `branches` so a business enables the feature branch by branch rather than business-wide on day one. Transfer itself follows PRD section 25 exactly: cancelling the original ticket safely, creating a new ticket at the destination branch, and linking the two through the new column — implemented as one atomic function (mirroring the shape of the `/tickets/join` and `/tickets/walk-in` endpoints from the Backend Schema document's section 17) so a transfer can never leave the customer with two active tickets or none. The destination ticket joins its branch's queue under the same strict FIFO rule as any other ticket (PRD section 35) — a transfer is not a way to skip ahead, only to relocate.

Customer app: a "Transfer to another branch" action on the Ticket Tracking Screen (App Flow section 7.6), available only while the ticket is still `waiting`/`almost_turn` (never after being called) and only when the current branch has the capability enabled, opening the same branch-comparison view PRD section 25 already describes — wait time, price, and travel time side by side — with the transfer replacing what would otherwise be a plain branch switch. Staff app: the equivalent action from Live Queue (App Flow section 8.5) for a receptionist assisting a customer who calls in, gated by the same per-branch flag and a capability check. Branch Settings (App Flow section 8.12) gets the on/off toggle for `allow_cross_branch_transfer`.

**Verification.** A test confirming a called or in-service ticket cannot be transferred. A test confirming the destination ticket's queue position follows normal FIFO ordering rather than any special placement. A test confirming the audit trail (`transferred_from_ticket_id` plus the corresponding `queue_events` rows on both tickets) is complete and correctly linked in both directions. A duplicate-transfer-attempt test, following the same idempotency pattern the first plan's Phase 4 established for joining a queue.

**Definition of Done.** With the flag enabled at both branches, a customer can transfer a waiting ticket end-to-end and see it appear correctly at the destination with the right position and wait estimate; the original ticket shows as cancelled-via-transfer, not a plain cancellation, in both the customer's history and the staff audit log; a called ticket correctly refuses the transfer action.

## 2. Phase 12 — Expanded Avatar Personalization and Animation

**Builds on:** the first plan's Phase 3 (onboarding, including the Phase 1 avatar picker) and Phase 4 (the Ticket Tracking Screen's live avatar, built under the PRD section 18 rule that the avatar visualizes queue state and never determines it).

**Scope.** Apply Backend Schema section 21.1's `customers.avatar_config` column. Build the build-your-own avatar picker (Design System section 8.1): four independently chosen parts — base/skin tone, hairstyle, hair color, top color — replacing the fixed 16-avatar grid at onboarding step 4 (App Flow section 5) and as the avatar-change flow in Profile (App Flow section 7.9), with a customer's existing Phase 1 `avatar_key` selection left untouched and still rendering correctly if they never revisit the picker (schema section 21.1's backward-compatibility note). Implement all eight PRD-defined animation states — Waiting, Moving Forward, Almost Your Turn, Called, Arrived, In Service, Completed, Cancelled — per the Design System's updated motion section, including the `motion-celebration` transition at chair arrival and its reduced-motion equivalent.

This phase is also where the PRD section 18 rule gets its first automated enforcement, not just a design intention: every one of these eight animation states must be provably derived from `queue_tickets.state` (and, for Called/Arrived, the relevant timestamp columns) at render time, never from a client-side timer, guess, or optimistic update that could show a state the engine hasn't actually reached.

**Verification.** A component test rendering each of the eight states from a given `queue_tickets` row and asserting the correct visual state and motion token are selected — parameterized so adding a ninth state later without updating this mapping fails the test rather than silently rendering the wrong thing. An integration test that artificially delays the animation layer (simulating a slow client) and asserts the textual position/status shown alongside it is still correct regardless — the PRD section 18 rule, made concrete. A Playwright test confirming the celebratory transition fires exactly once, at the `in_service` transition, both with and without `prefers-reduced-motion` set.

**Definition of Done.** A customer can build and save a custom avatar via all four parts, and it renders correctly at every size/context listed in the Design System's avatar section. All eight animation states are visually distinct and each is confirmed, by test, to be driven by real ticket state. The celebratory transition and its reduced-motion equivalent both work.

## 3. Phase 13 — In-App Customer–Barber Messaging

**Builds on:** Phase 12's avatar system (a conversation's header shows the other participant's avatar), the first plan's Phase 5 (barber interface and ticket assignment, since a conversation opens only once a barber is assigned), and Phase 7 (the real MessageBird/Web Push notification pipeline, reused here rather than rebuilt for message alerts).

**Scope.** Apply Backend Schema section 21.2–21.7 in full: the `conversations` and `messages` tables; the lifecycle triggers that close a conversation on ticket/appointment completion, cancellation, no-show, or barber reassignment; the `staff_view_conversation()` audited-access function and its backing `conversation_content_access_log` table; the RLS policies (participant-only direct access to `messages`, metadata-only staff visibility on `conversations`, no staff path to message content outside the audited function); the `view_message_content` capability, assigned only to Branch Manager and Owner; the Supabase Storage bucket for voice-note audio with its 30-day lifecycle rule; and the daily anonymization `pg_cron` job plus its paired Storage-deletion Edge Function.

Customer app: the Conversation Screen (App Flow section 7.12) — text and voice-note bubbles, the 60-second-capped record/playback flow using the browser's native `MediaRecorder`/`<audio>` APIs (tech stack document section 22 — no new dependency), the four quick-reply chips, delivered/read indicators, and the read-only state once the underlying ticket or appointment ends. Barber interface: the message entry point on Today's Queue (App Flow section 9.2), reachable without leaving that single working screen. Staff/admin portal: the Conversation Viewer (App Flow section 8.14) showing metadata by default, with the audited "View messages" action gated to Branch Manager/Owner and its own reason-entry step. New-message notifications reuse Phase 7's existing push/SMS pipeline exactly, including its push-to-SMS fallback for a barber who hasn't opened the app.

**Verification.** A test suite covering every lifecycle trigger in Backend Schema section 21.3: a conversation closes on ticket completion, on cancellation, on no-show, and — distinctly — a reassignment closes the old conversation and opens a genuinely new one rather than reusing the old thread. A test confirming a voice note over 60 seconds is rejected client-side and server-side. An RLS test confirming a customer cannot read another customer's conversation, a barber cannot read a conversation they're not part of, and — critically — that no staff role can select `messages.body` directly through PostgREST regardless of capability; only `staff_view_conversation()` can return it, and calling it writes exactly one `conversation_content_access_log` row. A test advancing a closed conversation's `closed_at` past 30 days and confirming the anonymization job clears `body`/`voice_note_storage_path` and the paired Edge Function removes the Storage object.

**Definition of Done.** A customer and their assigned barber can hold a full conversation — text, a voice note, and a quick reply — with correct delivery/read indicators and real push/SMS notifications on both sides. The conversation goes read-only the moment its ticket ends, and a reassignment produces a new, separate conversation rather than continuing the old one. A Branch Manager can view message content only through the audited action, and that access is visible in the Audit Log. The 30-day anonymization job is confirmed working against a manually backdated conversation.

## 4. Phase 14 — CRM and Reporting Depth

**Builds on:** the first plan's Phase 8 (`customer_segments` view, Reports, Business-Wide Dashboard) — this phase deepens that baseline rather than replacing it.

**Scope.** Two genuine gaps against PRD sections 28 and 31, both flagged explicitly in the Backend Schema document as illustrative-only at MVP time:

First, segmentation thresholds. Backend Schema section 13 noted the `customer_segments` view's 90-day/3-visit/3-no-show cutoffs were illustrative defaults, meant to move into `businesses.default_policies` "the moment the business wants them configurable." This phase does exactly that: the thresholds move out of the view's hard-coded literals into `businesses.default_policies` (read via a small helper function the view calls instead of a literal), and Settings (App Flow section 8.12) gets a form for an Owner to edit them, with the segmentation logic itself staying exactly as transparent and inspectable as PRD section 28 asks for — a business can now see *and change* the rule, not just see it.

Second, accurate historical revenue. PRD section 31 lists "revenue by branch and by service" as a Business KPI, hedged in the PRD's own text as "once tracked" — it's trackable now, since every completed ticket already carries a service and a branch, but doing it correctly requires knowing the price that actually applied *at the time of that visit*, not today's price, given effective-dated pricing (Backend Schema section 5) can change between then and now. This phase adds a `price_ghs_at_completion` column to `queue_tickets`, populated from `current_branch_service_price` at the moment a `service_sessions` row's `ended_at` is set (a small addition to the existing trigger in Backend Schema section 15.4), so revenue reporting is computed from a true historical snapshot rather than reconstructed from today's price table and quietly drifting wrong every time a price changes. Reports (App Flow section 8.13) and the Business-Wide Dashboard (section 8.4) both get a revenue-by-branch and revenue-by-service view built on this column, plus the remaining PRD section 31 KPIs not yet surfaced from the Phase 8 baseline — wait-time variance, appointment punctuality, and repeat-visit rate specifically, each computable from data the event log (`queue_events`) and `appointments`/`customers` tables already hold.

**Verification.** A test that changes a `branch_service_price` after a ticket has already completed and asserts that ticket's revenue figure in reporting is unaffected — proving the snapshot, not a live join, is what's actually being read. A test confirming a changed segmentation threshold in `businesses.default_policies` immediately changes which segment a borderline customer falls into, with no code deploy. Report-output tests for each newly added KPI against a seeded dataset with a known expected value.

**Definition of Done.** An Owner can edit segmentation thresholds from Settings and see `customer_segments` reflect the change immediately. Revenue-by-branch and revenue-by-service reports show figures that don't shift when a price is updated for future bookings. Wait-time variance, appointment punctuality, and repeat-visit rate all appear correctly in Reports and the Business-Wide Dashboard, completing PRD section 31's KPI list.

## 5. Phase 15 — Biometric (Passkey) Quick Login

**Builds on:** the first plan's Phase 1 (customer phone-OTP signup and staff password login) and Phase 3.3 (barber PIN login) — this phase adds an optional, faster path into accounts and sessions those phases already fully built, and changes nothing about how any of them work today.

**Scope.** No schema migration and no Edge Function, per Backend Schema section 3.5 — the entire server-side surface of this phase is a configuration change (enabling Supabase Auth's experimental passkey support in each Supabase project, `{ auth: { experimental: { passkey: true } } }`) plus client-side integration against `@supabase/supabase-js`'s `registerPasskey()`/`signInWithPasskey()` calls (tech stack section 23), already satisfied by the pinned SDK version with no upgrade needed. Customer app: the enrollment prompt on first password login per device and the Passkey/Fingerprint Setup screen (App Flow section 7.13), reachable from Profile. Staff/admin portal: the personal My Account passkey toggle in the header account menu (App Flow section 8.1) and the fingerprint option on Staff Login (App Flow section 8.2). Barber interface: the shared-station enrollment step (performed once per station, after a PIN login) and the fingerprint-or-PIN choice on Today's Queue login (App Flow section 9.1), for stations whose hardware supports it — a station without a fingerprint sensor is entirely unaffected and keeps working exactly as the first plan built it.

Because this feature's own vendor marks its API experimental (tech stack section 23), this phase starts with a re-verification step against Supabase's current passkey documentation before writing any integration code — confirming the method names, the opt-in flag, and the minimum SDK version are still accurate at the time this phase is actually reached, rather than trusting this document's snapshot of them.

**Verification.** An end-to-end test enrolling a passkey on a test device/authenticator (using a WebAuthn virtual authenticator in the test runner, the standard way to test this without physical hardware) and signing back in with it. A test confirming password login keeps working, unchanged, for an account that has never enrolled a passkey and for one that has. A test confirming a declined or failed biometric prompt falls back to the password field without an error state. For the shared-station case specifically: a test enrolling two different barbers' passkeys on the same simulated station and confirming each one's sensor touch signs in the correct barber, plus a test confirming PIN login still works unchanged on that same station throughout. A test confirming an Owner deactivating a staff account (existing behavior) also invalidates any passkey associated with it, per PRD section 47.5.

**Definition of Done.** A customer can enroll and then sign back in with a fingerprint/Face ID on a supporting device, with password login still fully functional as a fallback on the same account. The same holds for a staff member on their own personal device. A fingerprint-capable shared station lets an enrolled barber sign in with a touch, correctly resolving to that specific barber, while PIN login continues working on that station exactly as before for barbers who haven't enrolled or on stations without the hardware.

## 6. What Happens After This Plan

With this plan's Phase 15 complete, every item in PRD section 39's Phase 2 list is either already live (per section 0) or built here, PRD section 43 has no remaining open items — cross-branch transfer was the last one, resolved in Phase 11 — and PRD section 47's biometric login is live alongside every login path the first plan and this one already built. What's left is PRD Phase 3: the predictive/conversational AI direction described only at a high level in PRD section 27, deliberately left unspec'd until real production data from Phases 1–2 exists for it to build on — which is also exactly the order the PRD itself argues for. A third implementation plan, if and when that direction is scoped, would be the natural place to pick this numbering back up at Phase 16.
